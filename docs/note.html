1. The 60-second version

The whole project is one sentence:

Public taxi data on the internet
   → Azure Data Factory downloads it
      → ADLS Gen2 stores it raw
         → Databricks/PySpark refines it (Bronze → Silver → Gold)
            → SQL + a dashboard answer business questions

Two mental anchors that make everything else make sense:

Component Think of it as
Azure Data Factory (ADF) the worker — it fetches files and puts them somewhere. It never interprets them.
ADLS Gen2 the warehouse — shelves where files are stored exactly as they arrived.
Databricks + PySpark the factory floor — where raw material is cleaned, assembled, and turned into products.
SQL / dashboard the shop window — where people actually consume the result.

The single most important rule in the design: ADF moves bytes, Spark interprets them. Nothing gets parsed, cleaned, or fixed before it has been safely stored in its original form.

2. The Azure half — ingestion

2.1 The four building blocks (learn this and ADF is easy)

Everything in Data Factory is one of four things, and they stack in a strict order:

Linked Service  =  HOW do I connect?        (credentials + address of a system)
      ↓
Dataset         =  WHICH data / which path? (a pointer, possibly with "holes")
      ↓
Activity        =  WHAT do I do with it?    (copy it, look it up, loop over it)
      ↓
Pipeline        =  the whole orchestrated job

The reason this layering exists: activities never hold credentials or URLs. That indirection is what allowed this project to swap its data source three times without ever redesigning the pipeline.

2.2 The Azure resources

① Resource Group — rg-medallion-demo

The project folder in Azure. It holds every Azure resource so they can be found, billed, and deleted together.

rg-medallion-demo → Storage Account + Data Factory

Note: a resource group's own region only stores its metadata. Resources inside it can live anywhere — which is why this group is registered in East US while everything inside it runs in West US 2.

② Storage Account — stmedallionsajad01

The actual Azure storage service. One checkbox at creation time changed what it is:

Storage Account + "Enable hierarchical namespace" ✅  →  ADLS Gen2 (a real data lake)
Storage Account without it                        →  plain blob storage (a flat bucket)

Hierarchical namespace gives real directories, atomic renames, and POSIX-style permissions — the properties analytics engines like Spark need to treat storage as a filesystem. It cannot be enabled later; get it right at creation.

③ Container — datalake

The top-level bucket inside the storage account. Think of it as the root folder of all project data.

stmedallionsajad01 → datalake → (config/ … raw/ …)

④ Data Factory — adf-medallion-sajad01

The orchestration service. V2, West US 2, no Git integration (so "Publish all" is what saves work to the live factory).

2.3 The three files that matter

There are two kinds of files in this project, and keeping them apart is a design decision, not an accident.

months.json — the instruction file (config)

Location:  datalake → config → months.json

[{"month": "2025-01"}, {"month": "2025-02"}, … {"month": "2025-12"}]

Its only job is to tell ADF: "these are the 12 months I want you to download."

months.json → ADF knows which months to ingest

This is the metadata-driven pattern. The pipeline holds the logic; this file holds the scope. Want 2026 next year? Add a line to this file — no pipeline change, no redeployment.

NYC TLC monthly Parquet files — the main data

These live on NYC's public CDN. One file per month, ~55 MB, ~3 million trips each, containing pickup/dropoff timestamps, fare, distance, passenger count, and location IDs.

NYC TLC website → ADF → datalake → raw → tlc → yellow → month=2025-01 → yellow_tripdata_2025-01.parquet

taxi_zone_lookup.csv — the dictionary (reference data)

The trip files only say PULocationID = 132. That number means nothing on its own. This 265-row file translates it:

LocationID | Borough   | Zone
132        | Queens    | JFK Airport
161        | Manhattan | Midtown Center

So it is a dimension: supporting information that gives the facts their meaning. It goes to a different place, on purpose:

NYC TLC website → ADF → datalake → raw → tlc → reference → taxi_zone_lookup.csv

It sits in reference/, not inside the monthly folders, because it isn't trip data and it changes on a completely different rhythm (almost never).

2.4 The two connections (linked services)

ls_http_nyctlc — how to reach the source:

ADF → ls_http_nyctlc → NYC TLC website
      Base URL       = https://d37ci6vzurychx.cloudfront.net
      Authentication = Anonymous   (public open data, no key)

ls_adls_datalake — how to reach the destination:

ADF → ls_adls_datalake → your ADLS Gen2 account
      Authentication = Account key (selected from the subscription)

Now ADF knows both ends of the journey: ls_http_nyctlc = source, ls_adls_datalake = destination.

🏭 Production note: the account key would be replaced by the factory's managed identity plus a Storage Blob Data Contributor role assignment — then no secret is stored anywhere at all.

2.5 The three datasets

A linked service says "connect to this system." A dataset says "…and this specific data inside it."

ds_http_tlc_bin — which file on the website:

ls_http_nyctlc → ds_http_tlc_bin → a specific TLC file

parameter: relativeUrl   ← left as a "hole", filled at runtime

So the same dataset produces, one after another:

/trip-data/yellow_tripdata_2025-01.parquet
/trip-data/yellow_tripdata_2025-02.parquet
…

ds_adls_raw_bin — where to save it:

parameters: folderPath, fileName

For January they resolve to:
   folderPath = raw/tlc/yellow/month=2025-01
   fileName   = yellow_tripdata_2025-01.parquet

ds_adls_months_config — where the instruction file lives:

datalake → config → months.json

No parameters here: this file never moves.

Two design points worth remembering:

  • Parameter "holes" — one source dataset serves 12 different downloads; one sink dataset writes any path. Without them you'd need 12 datasets.
  • Format is a decision — source and sink use type Binary ("copy the bytes exactly, don't parse"), which enforces raw-zone immutability. Only the control file is type JSON, because the Lookup genuinely has to read its contents.

2.6 The activities

Lookup — lkp_months

Reads the instruction file. That's all.

months.json → Lookup → [2025-01, 2025-02, …, 2025-12]

It downloads no taxi data. ⚠️ Its "First row only" setting must be unchecked, or it returns a single object instead of the whole list.

ForEach — fe_download_months

Takes that list and repeats the same work for each element:

2025-01 → Copy
2025-02 → Copy
2025-03 → Copy
   …
2025-12 → Copy

With batchCount = 8, up to eight months download simultaneously — which is why 660 MB lands in ~2–3 minutes instead of ~20.

Copy — cp_tlc_to_raw (inside the loop)

The activity that actually moves the big files. One iteration:

current month = 2025-01
   → build the URL       → /trip-data/yellow_tripdata_2025-01.parquet
   → download the file
   → save it to          → raw/tlc/yellow/month=2025-01/

Its dynamic expressions:

source URL   @concat('/trip-data/', pipeline().parameters.service_type, '_tripdata_', item().month, '.parquet')
sink folder  @concat('raw/tlc/', pipeline().parameters.service_type, '/month=', item().month)
sink file    @concat(pipeline().parameters.service_type, '_tripdata_', item().month, '.parquet')

Where item() = the current element of the loop, and pipeline().parameters.x = a runtime knob. Retry is set to 2, so a transient network failure self-heals instead of failing the run.

Copy — cp_zone_lookup (standalone, no arrows)

The zone dictionary doesn't belong in the monthly loop — there's only one of it. So instead of Lookup → ForEach → Copy it's simply:

NYC website → cp_zone_lookup → datalake/raw/tlc/reference/taxi_zone_lookup.csv

Because it has no incoming arrow, it starts immediately when the pipeline starts and runs in parallel with the whole month loop. (Arrows in ADF mean "wait for that other activity first" — nothing else.)

The one connection to remember:

Linked Service = how to connect → Dataset = which data/path → Activity = what to do → Pipeline = puts them together

3. The bridge — how Azure hands data to Databricks

The data is in Azure. The compute is in Databricks (a separate account, a separate cloud). They need an authenticated handshake.

ADLS raw zone ──(SAS token: read + list only)──▶ Azure Python SDK ──▶ Unity Catalog Volume ──▶ Spark

Why a SAS token? A Shared Access Signature is a temporary, scoped, expiring credential. Ours grants read + list on one container, and nothing else, for one week (sp=rl). Compare that with the storage account key ADF uses: full control, no expiry. Handing Databricks the narrow credential instead of the master key is the principle of least privilege in practice.

Why copy files into a "Volume" instead of reading the lake directly? Databricks Free Edition is serverless-only — no cluster Spark configs, no dbutils.fs.mount, no Azure external locations. So the supported free-tier path is: Azure SDK downloads the files into a Unity Catalog Volume (governed file storage that Spark can read like a local disk), and Spark reads from there.

4.2 Why three layers

Each layer is a contract. That's what makes this an architecture instead of three scripts:

Layer Contract Why it exists
🥉 Bronze data exactly as it arrived, plus lineage columns. Nothing dropped, nothing fixed. Replay. If a bug is found in silver logic next month, rebuild from bronze — no re-downloading from the source.
🥈 Silver typed, validated, deduplicated; one row per business key. Truth. One clean dataset everyone downstream shares, instead of each report re-cleaning the data its own way.
🥇 Gold aggregated and denormalized, shaped to answer questions. Consumption. Analysts and BI tools write simple queries — no joins, no window functions.

4.3 🥉 Bronze — notebook 02_bronze_load

Job: get the files into Delta tables without touching the data.

Volume Parquet files → read → add lineage columns → write Delta table trips_raw

Three things the read does:

.option("basePath", …)                                  # makes month= a real column
.withColumn("_source_file", F.col("_metadata.file_path"))  # WHICH file each row came from
.withColumn("_ingested_at", F.current_timestamp())         # WHEN we processed it

_metadata.file_path is a hidden column Spark exposes on every file read — that's lineage, and it's the serverless-safe replacement for the old input_file_name().

What bronze deliberately does not do: no casting, no filtering, no renaming, no fixing. That is the contract.

Rerun safety:

if the table exists  → DELETE the current service's slice → append it again
else                 → create it, partitioned by month

Run the notebook five times, end up with one copy of the data. That property is called idempotency, and DELETE (impossible on plain Parquet) is what makes it clean here.

Partitioning: 40M rows ÷ 12 months ≈ 3M rows per partition — a healthy size, so month-filtered queries skip 11/12 of the data. (Partitioning a small table would be a mistake; knowing when not to partition matters as much as knowing how.)

4.4 🥈 Silver — notebook 03_silver_transform

The most substantial code in the project. Five distinct moves:

① cast types + derive features
② validate → quarantine failures
③ deduplicate
④ build a surrogate key
⑤ MERGE into the target table

① Types and derived features. Strings and raw columns become real types, and the calculations everyone would otherwise repeat get computed once:

duration_min = (dropoff_ts − pickup_ts) / 60
mph          = trip_distance / (duration_min / 60)
tip_pct      = tip_amount / fare_amount        # guarded: only when fare_amount > 0
pickup_hour, day_of_week, trip_date

The guard on tip_pct matters — an unguarded divide-by-zero produces Infinity, which silently poisons every average downstream.

② Data quality → quarantine, not silent drops. Ten domain rules run at once. Any row breaking one is written to trips_quarantine, tagged with the rule(s) it broke:

null_timestamp · dropoff_not_after_pickup · duration_over_12h
non_positive_distance · distance_over_200mi
negative_total · total_over_5000
implausible_speed (>100 mph) · bad_passenger_count · date_outside_2025

A taxi cannot arrive before it departs, travel at 300 mph, or bill $9,000. The important part isn't the rules — it's that rejects are kept and labelled. That converts "we lost some rows" into a queryable question:

SELECT _dq_rule, count(*) FROM workspace.tlc_silver.trips_quarantine GROUP BY _dq_rule;

③ Deduplicate. A window function keeps exactly one row per business key:

row_number() OVER (PARTITION BY vendor, pickup_ts, dropoff_ts, PU, DO, total  ORDER BY pickup_ts)  → keep rn = 1

④ Surrogate key. TLC trip records have no ID column — so one is manufactured:

trip_id = sha2( vendor | pickup_ts | dropoff_ts | pickup_zone | dropoff_zone | total_amount , 256 )

A deterministic hash of the columns that jointly identify a trip. Same trip in, same key out — which is what makes the next step possible.

⑤ MERGE — the idempotency guarantee.

MERGE INTO trips AS t USING batch AS s ON t.trip_id = s.trip_id
WHEN MATCHED     THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *

Reprocess the same month ten times and the table is identical: matched rows update in place, new rows insert, duplicates never accumulate. This is the block most worth being able to explain out loud.

4.5 🥇 Gold — notebook 04_gold_aggregates

Three tables, each answering a family of business questions. Built with CREATE OR REPLACE TABLE — a full recompute, which at this scale is simpler and safer than incremental logic (and Delta keeps every previous version anyway).

Table Grain Answers
daily_borough_revenue borough × day Where does revenue come from? How do boroughs compare on fare, tips, revenue per mile?
hourly_demand weekday × hour When is demand highest? And how fast does traffic move? (avg_mph = a congestion index derived from taxi meters)
zone_pair_flows origin × destination Which corridors matter? What are their economics?

zone_pair_flows joins dim_zone twice — once as origin, once as destination. That pattern has a name worth knowing: a role-playing dimension.

5. Delta Lake — versioning and time travel

Every table in bronze, silver, and gold is a Delta table, not a plain Parquet folder. Delta keeps a transaction log alongside the data, which is what makes MERGE, DELETE, and ACID guarantees possible in the first place — and it has a second benefit:

Because the tables are Delta tables, every write and MERGE creates a new version, so I can inspect table history and query an older snapshot using VERSION AS OF.

-- What has happened to this table, ever?
DESCRIBE HISTORY workspace.tlc_silver.trips;

-- Query the table as it was at version 0
SELECT count(*) FROM workspace.tlc_silver.trips VERSION AS OF 0;

-- Or as of a point in time
SELECT * FROM workspace.tlc_gold.ticker_kpis TIMESTAMP AS OF '2026-08-16';

Why this matters in practice: it gives auditability (every write is logged with its operation type and row counts), debugging (compare today's table against yesterday's to find what a change did), and recovery (restore a table to a prior version after a bad load, instead of rebuilding it from scratch).

6. Serving — SQL and the dashboard

The gold layer exists so that answering a question takes one simple query:

-- Demand and congestion by hour
SELECT pickup_hour, sum(trips) AS trips, round(avg(avg_mph), 1) AS avg_mph
FROM workspace.tlc_gold.hourly_demand
GROUP BY pickup_hour ORDER BY pickup_hour;

No joins, no window functions, no knowledge of how the data was cleaned — that work was already done, once, upstream. Two personas, two doors, one set of tables: engineers use notebooks, analysts use the SQL editor and the dashboard.

Findings worth pointing at:

  • Manhattan dominates trip volume; airport zones drive the highest-value corridors.
  • Average speed inverts demand — slowest in late-afternoon rush, fastest pre-dawn. A traffic index, derived from taxi meters.
  • Tipping varies by borough and payment type.

7. Incident log — the data-source saga

The pipeline was built against two other data sources before NYC TLC. Nothing about the pipeline's shape ever changed — only a connection, an expression, and the config file.

# Source What happened Lesson
1 stooq.com (stock CSVs) Deployed a JavaScript proof-of-work anti-bot challenge mid-build. ADF can't execute JS, so it faithfully landed HTML challenge pages. Every copy activity reported success. Validate landed content, not HTTP status. Green runs can still produce garbage.
2 Alpha Vantage (stock API) Re-pointed everything, throttled politely… then the backfill returned {"Information": "outputsize=full is a premium feature"} with HTTP 200. Free tier = 100 days only. Verify a free tier's exact scope before designing on top of it.

8. Runbook — operating it

Run the ingestion: ADF Studio → Author → pl_ingest_tlc_monthly → Debug → accept service_type = yellow. ~2–5 minutes. Safe to re-run (same paths get overwritten).

Add a new month: TLC publishes with a ~2-month lag. Append {"month": "2026-06"} to months.json, re-upload, run the pipeline, then re-run notebooks 02 → 04. Silver's MERGE absorbs any overlap.

Ingest green taxis: run with service_type = green. Same pipeline, parallel folder tree — that parameter earning its keep.

Debug a copy activity: Output tab → hover the row → input icon shows the resolved URL for that iteration (expression debugging) → glasses icon shows bytes read/written.

Refresh the lakehouse: notebooks 01 → 02 → 03 → 04, in order. Notebook 01 needs a fresh SAS token if the old one expired.

Cost safety: the schedule trigger exists but stays Stopped. Storage is ~700 MB ≈ pennies. Full teardown = delete the resource group rg-medallion-demo (one action) — the Databricks half survives permanently at $0.

9. Interview sound bites

  • "ADF only moves bytes — the raw zone is byte-for-byte and date-partitioned. Nothing parses data before bronze, so I can always replay."
  • "The pipeline is metadata-driven: changing scope is a config-file edit, not a deployment."
  • "TLC trips have no natural key, so silver builds a SHA-256 surrogate key and MERGEs on it — reprocessing a month is idempotent by construction."
  • "Bad rows aren't dropped, they're quarantined with the rule they violated, so data quality is a queryable metric rather than a vague claim."
  • "Because the tables are Delta, every write and MERGE creates a new version — I can inspect table history and query an older snapshot with VERSION AS OF."
  • "All thirty copy activities were green and the data was still garbage — that's why I validate landed content, not HTTP status codes."
  • "Free Edition is serverless-only, so I bridged storage with a scoped read-only SAS into a Unity Catalog Volume. On a paid workspace I'd register an external location and read abfss:// in place."

10. Glossary

Term Meaning
ADLS Gen2 Azure Data Lake Storage Gen2 — blob storage with a hierarchical namespace (real directories)
Hierarchical namespace The setting that turns blob storage into a data lake. Creation-time only.
Linked service An ADF connection definition: how to reach a system, with what credentials
Dataset An ADF pointer to specific data on a connection; may carry parameters
Activity One unit of work in a pipeline (Lookup, ForEach, Copy…)
Metadata-driven The pipeline holds logic; a config file holds scope
Raw zone Immutable, as-received storage — the replay point of the platform
Hive-style partitioning Encoding a column in the folder name (month=2025-01) so engines read it as data
Medallion architecture Bronze (raw) → Silver (clean) → Gold (aggregated) layering
Delta Lake Storage format adding ACID transactions, MERGE/DELETE, and versioning to Parquet
MERGE / upsert Update matching rows, insert new ones — in one atomic operation
Idempotency Running the same job repeatedly leaves the same end state
Surrogate key An engineered identifier when the source has no natural one
Quarantine table Where rows that fail validation are stored with the reason
Dimension Reference data giving facts their meaning (zone → borough)
Role-playing dimension The same dimension joined twice in different roles (origin, destination)
SAS token Shared Access Signature — a scoped, expiring storage credential
Unity Catalog Volume Governed file storage in Databricks, readable like a local path
Time travel Querying a previous version of a Delta table (VERSION AS OF)
